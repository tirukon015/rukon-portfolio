ResearchForge , project presentation

Live Entirely new. This project was absent from the site.

AI research paper assistant · independent project

An AI research assistant built to say when the paper doesn't support the answer.

Upload an academic PDF and get a structured summary, a research-gap analysis where every gap carries the evidence it rests on, and a literature review scoped to the prior work the paper itself discusses. A Python/FastAPI backend and a Next.js frontend deployed as one project behind a single origin.

01Upload a PDF→ 02Validate and extract→ 03Analyse→ 04Read the structured result

Implemented / available / not connected

This distinction is the most important thing on the page. “It exists in the repository” and “it runs in production” are different claims.

StateCapabilityDetail
ImplementedUpload, validation, extractionDouble validation, PDF signature check, encryption and scanned-file rejection.
ImplementedSummary, gaps, literature reviewThree schema-constrained model calls, each validated on return.
ImplementedProvider abstractionGemini and Anthropic behind one interface. Gemini is the configured default.
ImplementedConditional chunkingWhole-document by default; map-reduce only above a character threshold.
Built, not liveResearch library & cross-paper reviewPages, routes, repository, schemas and prompt written and tested. Without a database every route answers 503 rather than pretending the library is empty.
Not connectedEmbedding providerInterface and request construction written and unit-tested offline. The HTTP call is deliberately not implemented, so no embedding is ever produced.
Not connectedRetrieval / vector searchNot implemented. The analysis path sends the document, not retrieved passages. This is not a RAG system.
Not connectedDatabase (Supabase / pgvector)Migrations, repository and Supabase implementation exist and are tested against a mock. No project connected, nothing persisted.

Why this table is an asset rather than an admission. Published limitations are rare and disproportionately trust-building with technical readers. A hiring manager who reads “this is not a RAG system” on a candidate's own site learns more about their judgement than any capability claim would tell them.

Limitations, stated on the page

  • Nothing is saved. Reloading the tab discards the analysis.
  • No OCR, so scanned papers with no text layer are rejected rather than processed.
  • The literature review covers only the prior work one paper discusses. It does not search a corpus.
  • No authentication and no rate limiting. Acceptable only while the application stores nothing.
  • Papers are identified by filename , bibliographic metadata extraction is not implemented.

07

Engineering evidence

Nineteen mechanisms verified at source level in the second pass. These are what make the capability claims checkable rather than assertable. Available for writing

RPOMS

  • Malaysian business-day boundary , a UTC server would not roll the day over until 8am local, long enough for a morning delivery to file under yesterday
  • Read deadlines , added after a measured incident: 1.2s on one attempt, still hanging ninety seconds later on the next
  • The UNREAD sentinel , where a fallback would be dishonest, callers get a distinct value and decide for themselves
  • Security headers in middleware , nosniff, DENY, strict-origin, Permissions-Policy on every response
  • Supabase pooler handling , prepared statements off, because PgBouncer transaction pooling does not support them
  • OOXML run-splitting , Word splits a line across runs, so a placeholder can straddle several; two passes fix it
  • Longest-prefix serial rules with Excel COUNTIF-compatible duplicate keys
  • Preferred-spelling names , display the spelling the office uses most, not an invented capitalisation
  • Whole-history inventory , a documented refusal to window, because a window reads high and does so quietly

ResearchForge

  • Cross-paper review , built from stored analyses, not by re-reading PDFs, with the cost stated in the module
  • Asymmetric retrieval design , questions and passages embedded differently, which most implementations discard
  • Dimension permanence , 1024 is baked into the column; embedding_model per row is what makes a switch survivable
  • Licence-driven dependency choice , the faster PDF library is AGPL, incompatible with an MIT repo
  • Conservative text cleaning , ligatures, hyphenation, whitespace that never crosses newlines
  • Deliberately sequential calls , parallelism multiplies rate-limit burden for a latency win that does not matter
  • Cross-vendor model guard , a leftover model name falls back to the provider's own default
  • 503, not an empty list , “an empty list is a claim, and a deployment with no database is not in a position to make it”
  • Vendor-neutral error hierarchies, applied independently to generation and to storage

Related writing & the two-way project relationship

The mechanism that turns project work into blog authority. Both directions are derived from one field, so they cannot drift apart. Live

Project → blog

Each case study renders a “Writing from this work” section, built by getPostsForProject(). It reads the structured relatedProjects field and falls back to the older hand-written related links, so no existing relationship was lost in the migration.

/work/rpoms10 articles , production systems, admin panels, reporting, maintenance, automation, internal UX
/work/erth4 articles , the design-to-code group, all four flagged for merge or retirement
/work/researchforge0 articles today , 36 planned. This is the largest single content opportunity in the plan.

Blog → project

Each article renders a “The work behind this” panel above its Related links, showing the project name and its tagline rather than a bare link, so the reader knows what they are clicking into.

Article→ its case study · its category page · 2, 3 curated sibling articles
Category page→ its anchor project · all its articles · the blog index
Homepage→ /work · all three case studies · latest three articles · capability evidence links
Experience entry→ the case study that role produced

Related-article selection

getRelatedPosts() was category-only, which degrades to near-random as a category grows. It now takes hand-picked relatedPosts first and fills any remaining slots from the same category , so a curated pair always wins, and the fallback still works at 200 articles.

The sequencing consequence. Writing the AI cluster before the ResearchForge case study existed would have meant 36 articles with nowhere authoritative to link. Writing the SEO cluster before the ERTH rewrite would have meant 28 articles pointing at a page describing different work. Both case studies now exist, so both clusters are unblocked.
